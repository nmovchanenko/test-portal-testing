## Why

Sign-up is the entry point to TestPortal (`POST /api/v2/auth/signup`, `TestPortal-client`'s `/signup` page) but has zero automated coverage today — `playwright-ts/tests/{api,ui,mocking}` are all empty aside from a seed test. Sign-up also has non-trivial, easy-to-regress business rules split across two layers (client-side zod schema in `authSchemas.ts` and server-side checks in `userService.signup`/`authProviderService.signup`, including the `@ventionteams.com` domain restriction, duplicate-email handling, and a pending-approval account lifecycle), which makes it a good first real feature to test and a template for how future features get covered across the pyramid.

## What Changes

- Add API-level tests (`playwright-ts/tests/api`) hitting `POST /api/v2/auth/signup` directly: valid signup, missing fields, invalid email format, weak/short password, non-`@ventionteams.com` domain rejection, duplicate email rejection, response shape (`201` + safe user with `status: "pending"` + distinct `message`, no password hash leaked; `400` + distinct `error` text per failure cause). This is the only level where the backend's per-cause error/success text is actually observable (see Impact).
- Add mocked UI tests (`playwright-ts/tests/mocking`) that render the Signup page against a mocked/stubbed API to exercise client-side zod validation (name/email/password/confirm-password rules, inline error messages, disabled/loading button state) and the two UI-level outcome branches: the generic success message + redirect to `/login`, and the generic failure message + staying on `/signup` with input retained. (Client-side zod does not enforce the `@ventionteams.com` domain restriction, so a mocked "wrong domain" case is really just the generic-failure branch, not a distinguishable UI state.)
- Add a small number of E2E UI tests (`playwright-ts/tests/ui`) that drive the real signup flow end-to-end against a running TestPortal-backend + client: one happy-path signup → redirect to `/login` with the (generic) success message, confirming a subsequent login attempt is correctly blocked with `403`/pending-approval messaging since the new account is not active; and one representative failure path (duplicate email) surfaced as the generic failure message on `/signup`. Kept minimal per the testing pyramid — API and mocked-UI tests carry the bulk of validation coverage.
- Tests are hand-authored directly against this change's own `specs/` (scenarios) and `design.md` (implementation approach) artifacts, using `playwright-cli` for live verification against the running app during authoring — no `playwright-test-planner`/`generator`/`healer` agents are used for this change (see design.md for why).
- No changes to application code — this is test-authoring only, though the exploration below surfaced a couple of product behaviors (see Impact) worth flagging to the team even if out of scope for this change.

## Capabilities

### New Capabilities
- `playwright-ts/signup-testing`: Automated test coverage for the sign-up feature across API, mocked-UI, and E2E levels, following the testing pyramid and produced via the planner → generator → healer agent workflow.

### Modified Capabilities
(none — `playwright-ts` scaffold and `playwright-test-authoring-agents` specs already anticipate this usage; no requirement changes needed there)

## Impact

- **New files**: test specs under `playwright-ts/tests/api/`, `playwright-ts/tests/mocking/`, `playwright-ts/tests/ui/`, plus any shared fixtures/helpers (e.g. signup payload builders, unique-email generation to avoid cross-run collisions).
- **Systems under test**: `TestPortal-backend` (`POST /api/v2/auth/signup`, `userService.signup`, `authProviderService.signup`), `TestPortal-client` (`/signup` page, `useSignup` hook, `authSchemas.ts` zod schema).
- **Test data / environment**: API and E2E tests need a reachable TestPortal-backend instance (local dev stack per root `CLAUDE.md`) and email addresses ending in `@ventionteams.com` to pass server-side domain validation; needs a strategy for unique emails per run and cleanup/isolation so repeated runs don't collide on duplicate-email checks.
- **Confirmed via live exploration** (`playwright-cli` against the running dev stack, backend `AUTH_PROVIDER=local` per `GET /api/v2/auth/config`) — these correct/extend assumptions from the first pass at this proposal:
  - **Signup does not activate the account.** A successful signup creates the user with `status: "pending"`; the account needs admin approval before login works. Immediately logging in with the just-created credentials returns `403` with `{"error":"Your account is pending administrator approval."}`. Any "happy path" scenario must account for this rather than treating post-signup login as immediately possible.
  - **The client discards backend response detail.** `useSignup.ts`'s catch handler always renders the same hardcoded string ("Failed to create account. Please try again.") regardless of cause, and the success path always renders a hardcoded "Account created successfully! Please sign in to continue." instead of the backend's actual `message`/`error` text. Confirmed live: duplicate-email (`400`, `"An error occurred during registration. Please try again or contact support."`) and wrong-domain (`400`, `"Registration not allowed"`) both render identically in the UI. **Consequence for the test plan**: per-cause message assertions belong only in the API-level tests; mocked-UI/E2E tests can only assert the generic string and page state (stayed on `/signup` vs. navigated to `/login`).
  - **No `<label>`/`htmlFor` association.** `FormField` renders a plain `<Text>` as a visual label with no `id`/`htmlFor` link; each input's accessible name comes from its placeholder text instead. Tests must target fields via `getByRole('textbox', { name: '<placeholder text>' })`, not `getByLabel`.
  - **Two equivalent signup routes exist** server-side: `POST /api/v2/auth/signup` (what the client actually calls) and `POST /api/v2/users/signup` (a "compatibility" alias hitting the same handler). Proposing to cover only the primary route at the API level unless the team wants explicit alias-route regression coverage too.
  - **Auth is provider-pluggable** (`local` vs `cognito`, via `AUTH_PROVIDER`), with materially different signup side effects — `local` yields pending-approval accounts, `cognito` sends an email-verification flow instead, per `authProviderService.ts`. This suite targets the `local` provider (the confirmed local dev default); tests should assert against `GET /api/v2/auth/config` or otherwise guard against running against a `cognito`-configured environment.
- **No production code changes** — scoped entirely to `playwright-ts/`.
